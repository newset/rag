WEBPACK

Loader 与 Plugin：两套完全不同的扩展机制

Webpack 的心智模型是"先构建完整依赖图，再统一打包"。Compiler 是全局唯一、贯穿整个生命周期的对象，持有完整配置；每次编译（watch 模式下每次重新编译）都会创建一个新的 Compilation 实例，记录当次构建的模块、依赖图、chunk 与产物信息。两者都基于 Tapable 这套事件流库暴露 hook —— Loader 和 Plugin 正是挂在这套 hook 体系两个不同粒度上的扩展点。

Loader 单文件转换器

本质是一个接收源码、返回转换后源码的 Node 函数，作用范围是单个模块，感知不到整个依赖图。

  • 职责：把"非 JS 语义"的资源转成 webpack 能处理的 JS 模块 —— babel-loader（ES6+ → 兼容语法）、ts-loader、css-loader/style-loader、vue-loader、asset modules（替代旧版 file-loader/url-loader）。
  • 执行顺序：数组从右到左、从下到上链式调用；每个 loader 还有 pitch 阶段，先从左到右跑一遍（用于提前拦截/短路后续 loader）。
  • 接口：this.async() 声明异步、this.getOptions() 取配置、可返回 source map。
// 一个最简单的 loader
module.exports = function(source) {
  const result = transform(source);
  return result; // 转换后的代码字符串
};

Plugin 全生命周期扩展

本质是一个带 apply(compiler) 方法的类，通过 tap / tapAsync / tapPromise 订阅 compiler、compilation 生命周期上的具体 hook。

  • 职责：触达"整个构建流程" —— 启动、模块解析、chunk 划分、asset 生成、优化压缩，几乎每个阶段都有对应 hook。典型：HtmlWebpackPlugin、MiniCssExtractPlugin、DefinePlugin、Module Federation。
  • 能力边界：Loader 做不到的事，比如重新划分 chunk、注入全局变量、在打包结束后额外生成/修改产物文件。
  • 与 Loader 的分工：Loader 解决"如何读懂一个文件"，Plugin 解决"如何组织整条构建流水线"。
// 一个最简单的 plugin
class MyPlugin {
  apply(compiler) {
    compiler.hooks.emit.tapAsync(
      'MyPlugin',
      (compilation, cb) => { /* ... */ cb(); }
    );
  }
}
VITE

没有"先打包再启动"这一步

Vite 的心智模型反过来："先启动，按需编译"。开发模式下浏览器原生按 ESM 请求文件，Vite 收到请求才编译对应的单个文件并返回 —— 启动时间因此和项目里模块总数基本无关，这是它与 webpack 开发体验差异最大的根源。

依赖预构建 esbuild

第三方依赖体量大、更新频率低，很多还是 CommonJS/UMD 格式。Vite 用 esbuild（Go 编写，比纯 JS 工具快一到两个数量级）在启动时把它们转成 ESM，并把每个包内部零散的模块合并成少数几个文件。

  • 解决两个问题：CJS/UMD → ESM 的格式兼容；把一个包内几十上百个小模块合并，避免浏览器发起过多请求瀑布。
  • 结果缓存在 node_modules/.vite，依赖没变化时直接复用。
  • 这一步只处理 node_modules，业务代码不会被这里预打包。

Vite Plugin Rollup 接口超集

Vite 插件接口兼容 Rollup 的 resolveId / load / transform 等钩子，同时扩展了开发服务器专属的钩子。

  • configureServer：直接操作底层 connect 服务器实例，相当于中间件。
  • transformIndexHtml：转换 index.html。
  • handleHotUpdate：自定义 HMR 行为。
  • apply: 'serve' | 'build' 与 enforce: 'pre' | 'post' 控制插件在哪个阶段生效、执行顺序。
// Vite 插件骨架
export default () => ({
  name: 'my-plugin',
  enforce: 'pre',
  transform(code, id) { /* ... */ }
});

生产构建

开发环境不打包，但线上仍需要产物：传统上 Vite 生产构建交给 Rollup（tree-shaking 彻底、输出干净）。从 Vite 7 起可选切换到 Rolldown（Rust 编写、兼容 Rollup 接口的打包器）大幅提速，Vite 8 起 Rolldown 成为默认打包器 —— 详见下方"版本演进"。

VITE架构演进

Vite 版本演进：从"双引擎"到"统一 Rust 引擎"

这条时间线的主线，是"开发用 esbuild、生产用 Rollup"这套务实的双引擎组合，如何被同一批 Rust 工具逐步统一替换。

1
v12020.12

面向 Vue 单文件组件的实验性开发服务器，与 Vue 强绑定，还不是通用构建工具。

2
v22021.02

架构重写：插件接口对齐 Rollup，变成框架无关的通用工具；开发阶段引入 esbuild 做依赖预构建与 TS/JSX 转译。今天所说的"Vite 架构"基本从这一版定型。

3
v32022.07

优化配置解析与 base 路径处理，dev / build 行为进一步对齐，SSR 能力增强。

4
v42022.12

升级 Rollup 3，构建性能与产物体积优化。

5
v52023.11

升级 Rollup 4（核心 parser 用 Rust 重写以提速），要求 Node 18+，为后续多运行时能力打基础。

6
v62024.11

引入实验性 Environment API：把"浏览器 client / SSR / Edge runtime / Worker"抽象成可插拔的多个 environment，为非浏览器运行时（如 Cloudflare Workers）提供统一的构建心智模型。

7
v72025

推出可选的 rolldown-vite 包，把 Rust 编写、兼容 Rollup 接口的 Rolldown 作为可插拔替代打包器；新增 buildApp 钩子支持跨 environment 的插件协作；默认浏览器 baseline 提升（Chrome 87→107 等），发布形态改为纯 ESM，要求 Node 20.19+ / 22.12+。

8
v82026

Rolldown 转正为默认且唯一的打包器，取代"dev 用 esbuild、build 用 Rollup"的双引擎架构；与 Oxc 工具链（同一批 Rust parser/transformer）对齐，官方宣称构建速度提升 10–30 倍，同时保留对现有 Rollup/Vite 插件的兼容层。

核心模块演进

为什么会走向统一：一条更长的技术脉络

把版本号背后的动机连起来看，会更清楚"Vite 8 默认切到 Rolldown"这件事在解决什么问题。

  • 起点问题：JS 生态的构建工具长期是"用 JS 写 JS 工具"——webpack、Rollup 早期实现都是纯 JS，大规模 AST 遍历和字符串处理天然受制于 JS 本身的性能。
  • 第一波系统语言重写：esbuild（Go，Evan Wallace）率先证明了用系统语言重写 transform/bundle 热点路径能带来数量级的性能提升；随后 swc（Rust）、Rspack（Rust，字节跳动出品，尽量兼容 webpack 的 loader/plugin 配置）、Turbopack（Rust，Vercel/Next.js）相继出现，走的是同一条路：不改变现有心智模型，替换掉性能瓶颈的执行引擎。
  • Vite 2 的务实选择：dev 用 esbuild（重启动速度、转译够用），build 用 Rollup（重产物质量、tree-shaking 更彻底）——本质是在当时 Rust/Go 工具链还不够成熟、esbuild 又不追求做到 Rollup 级别打包质量的情况下，用两套引擎覆盖两种场景的折中方案。代价是 dev 和 build 走两套转译/打包语义，长期存在"esbuild 转译结果和 Rollup 打包结果不完全一致"导致的边缘 bug。
  • 走向统一：Vite 作者 Evan You 创立 VoidZero，目标是用一套 Rust 工具链同时覆盖 dev 和 build 两个场景——Oxc 负责 parser / transformer / linter，Rolldown 负责打包，二者共享同一套底层设施。Vite 7 的 rolldown-vite 是过渡期的可选项，Vite 8 让它成为默认，标志着 Vite 从"胶水层 + 双引擎"演进为"自有 Rust 统一引擎 + 插件生态兼容层"。
  • 和 webpack 生态的呼应：webpack 核心至今仍是 JS 实现，但 Rspack 在做的是相同方向的事——保留 webpack 的配置项、Loader/Plugin 心智模型，把执行引擎换成 Rust，尽量做到"改一行配置就能迁移"。两条生态路径（Vite→Rolldown、Webpack→Rspack）殊途同归，都是"接口不变、引擎换成系统语言"。
